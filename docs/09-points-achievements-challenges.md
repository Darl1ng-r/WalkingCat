# Phase 9 — Points, Achievements & Challenges

## Goal
Reward healthy, legitimate activity with points, a small set of achievements, and daily/weekly challenges. Everything is **computed server-side**, idempotent, capped against farming, and never punishes rest days.

## Prerequisites
- Phase 5 (walks + daily activity) and Phase 8 (accepted sightings/cats).

## Out of scope
- Friend/group challenges and leaderboards (Phase 10).
- Rewards store, cosmetics unlock UI (post-MVP — points may be displayed only).
- Push notifications for challenges (Phase 12 optional).

## Point rules (initial — stored in `app_config`, authoritative in SQL)

| Event | Points | Limits |
|---|---|---|
| Completed walk (≥ 0.5 km **and** ≥ 10 min moving, not suspicious) | 20 | max 3 rewarded walks/day |
| Distance bonus | +5 per full km | capped at 10 km per walk |
| Daily step milestone (5k / 8k / 10k) | 10 / 10 / 10 | once per day each |
| Accepted cat sighting | 15 | max 5 rewarded sightings/day |
| Achievement unlocked | per definition | once ever |
| Daily challenge completed | 25 | once per challenge instance |
| Weekly challenge completed | 75 | once per challenge instance |

**Never** award points for: calories, rare-looking cats, specific locations, repeated photos, or approaching cats.

## Data / schema
Migration `<ts>_gamification.sql`:
- `points_ledger` (append-only): `id`, `user_id`, `amount int`, `reason text`, `source_type text` (`walk`,`walk_distance`,`steps_milestone`,`sighting`,`achievement`,`challenge`), `source_id text`, `created_at`. **Unique(`user_id`,`source_type`,`source_id`)** → idempotent. No client insert/update/delete.
- View/function `get_points_summary()` → total, this week.
- `achievements` (seeded): `id` (slug), `title`, `description`, `icon`, `points`, `metric`, `threshold`.
- `user_achievements`: `user_id`, `achievement_id`, `unlocked_at`, unique pair.
- `challenges` (seeded templates): `id`, `period` (`daily`/`weekly`), `metric` (`walks`,`distance_m`,`steps`,`active_days`,`sightings`), `target`, `title`, `difficulty` (`easy`/`standard`).
- `challenge_instances`: `challenge_id`, `period_start date`, `period_end date` (generated by pg_cron daily/weekly, 2–3 daily + 1–2 weekly active at a time).
- `challenge_progress`: `user_id`, `instance_id`, `progress numeric`, `completed_at`, unique pair.
- Server functions/triggers:
  - `on_walk_inserted` → award walk + distance points, update challenge progress, evaluate achievements.
  - `on_sighting_accepted` → award sighting points (respect daily cap), progress, achievements.
  - `on_daily_activity_upserted` → step milestones, step challenges.
  - `evaluate_achievements(user_id)` — idempotent.

### Seed achievements (MVP)
First walk · First cat discovered · 5 / 25 / 100 walks · 10 / 50 / 100 km total · 5 / 25 / 50 cats in collection · Walked on 3 different days in a week · Walked on 5 different days in a week.

### Seed challenge templates
Daily (easy): 10-minute walk · 3,000 steps · 1 km walk.
Weekly: 3 walks · 10 km total · walk on 4 different days · 2 cat sightings (*any* place/time — never location-based).
**Adjustable goals:** user picks "Easy / Standard" challenge level in settings; easy targets ≈ 60%.

- [x] Caps enforced (4th walk of the day: 0 walk points; 6th sighting: 0 points but still collected).
- [x] Achievements unlock at correct thresholds, once.
- [x] Challenges progress from walks, steps, and sightings; complete once.
- [x] Client cannot insert into `points_ledger` (verified).
- [x] No streak-loss or negative messaging.

## Pitfalls
- All award logic in **one place** (SQL). Client only displays.
- Use `security definer` functions carefully: set `search_path`, check `auth.uid()`.
- Keep point values in config so tuning after the beta needs no app release.

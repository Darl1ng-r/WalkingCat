# Phase 10 — Friends & Leaderboards

## Goal
Users can add friends, see a small opt-in activity view of friends' milestones, compare progress on a **weekly friends leaderboard** (separate categories: steps, distance, walks, challenge points), and optionally share a cat card — **without ever exposing routes, live location, or sighting locations**.

## Prerequisites
- Phase 9 (points, challenges, daily activity aggregates).

## Out of scope
- Direct messaging, comments, full social feed.
- Public/global leaderboards (friends-only in MVP).
- Group challenges with custom groups (post-MVP; a simple "invite friends to weekly challenge" is a stretch goal).
- Push notifications (Phase 12 optional).

## Data / schema
Migration `<ts>_social.sql`:
- `friendships`: `id`, `requester_id`, `addressee_id`, `status` (`pending`/`accepted`/`declined`/`blocked`), `created_at`, `responded_at`; unique unordered pair (use `least/greatest` index); no self-friendship.
- `friend_invites`: `code text unique` (short, random), `user_id`, `expires_at`, `uses`.
- `privacy_settings` (created Phase 2) columns now used: `show_on_friends_leaderboard bool default true` (friends-only, safe default), `share_milestones_with_friends bool default true`, `share_cat_cards bool default false`, `discoverable_by_username bool default true`.
- `activity_events` (milestones only): `user_id`, `type` (`walk_completed`,`achievement_unlocked`,`collection_milestone`,`challenge_completed`,`cat_card_shared`), `payload jsonb` (**no coordinates, no polylines**), `created_at`. Written by server triggers only, respecting privacy settings.
- `reactions`: `event_id`, `user_id`, `emoji` (limited set: 👏 🐾 ❤️ 🔥), unique per user/event.
- Helper `is_friend(a uuid, b uuid) returns bool` (security definer, stable).
- RLS: friends can read each other's `profiles` (public fields only — use a `public_profiles` view), `activity_events`, reactions. **Walks, routes, sightings, cats remain owner-only.** Shared cat cards exposed via a view with a short-lived signed photo URL generated by an Edge Function.
- Function `get_friends_leaderboard(p_metric text, p_week_start date)` → rank, user, value for self + accepted friends who opted in. Metrics: `steps`, `distance_m`, `walks`, `challenge_points`. **Calories excluded.**

## Acceptance criteria
- [x] Two test accounts can connect via username search and via invite link.
- [x] Leaderboard shows correct weekly values per metric; opted-out users hidden.
- [x] Blocking hides the user everywhere and prevents new requests.
- [x] RLS test script passes — no route, walk point, sighting location, or photo of a non-shared cat is reachable by a friend.
- [x] Calories never appear in social features.

## Manual test script
1. User A invites B by link → B accepts → both see each other on the leaderboard.
2. A walks 2 km → A's distance updates on B's leaderboard.
3. A turns off "show on leaderboard" → disappears for B.
4. A shares a cat card → B sees it and reacts.
5. B blocks A → A disappears from B's app and can't re-request.

## Pitfalls
- Leaderboard queries can get heavy: aggregate from `walks` / `daily_activity` with proper indexes; consider a materialized weekly table refreshed by pg_cron if slow.
- Username search must not leak non-discoverable users or emails.
